# Use Case: Report Problem with Trip

## Goal in Context

A rider's client application submits a user-generated problem report regarding a specific transit trip (for example, if the vehicle never arrived, arrived early or late, displayed the wrong destination headsign, or bypassed a stop). The server records the report for review by transit operations.

## Scope

OneBusAway REST API —
- `GET /api/where/report-problem-with-trip/{id}`
- `GET /api/where/report-problem-with-trip.json`

*(Note: The legacy Java Struts implementation supported `/api/where/report-problem-with-trip/{id}.json` and mapped `show`, `create`, and `index` to the same handler, accepting both GET and POST requests. Maglev registers both `GET /api/where/report-problem-with-trip/{id}` and `GET /api/where/report-problem-with-trip.json`. A trailing `.json` in the path does not become part of `{id}`, as `ExtractIDFromParams` (`internal/utils/http.go:11`) trims `.json` from the path parameter.)*

## Level

User goal

## Primary Actor

Rider (via a client application)

## Stakeholders and Interests

- **Rider** — wants to report a service anomaly with a scheduled trip and receive immediate confirmation.
- **Transit Agency / Operations** — wants timely, detailed rider incident reports (including vehicle ID, service date, stop context, and user location) to detect service disruptions and schedule adherence issues.
- **Client Application** — expects a consistent response envelope and predictable parameter binding across client libraries.

## Preconditions

- The caller supplies a valid API key (`key=<key>`).
- The trip ID parameter is provided either as query parameter `tripId` (e.g., `tripId=1_12345`) or as the URL path segment `{id}` in the combined `agencyId_tripId` format.

## Minimal Guarantees

- All responses generated by the endpoint handler include `code`, `currentTime`, `text`, and `version` (client-canceled requests produce no response; router-level 404 responses for unmatched routes or 405 responses for unsupported methods are rejected before handler invocation).
- Non-context database storage failures return HTTP 500 with a standard JSON error envelope (`"internal server error"`, `version: 2`); context deadline expirations return HTTP 504, and canceled requests return client-canceled responses (producing no response when the client disconnected).
- Malformed coordinates, accuracy, or boolean values return HTTP 400 with a field validation error envelope.

## Success Guarantees

- The problem report is stored in the database (`problem_reports_trip`) with timestamps (`created_at` and `submitted_at`) set to the current server time in milliseconds.
- Omitted optional parameters are stored as database `NULL`.
- HTTP status 200 is returned with a standard JSON response envelope containing `code: 200`, `text: "OK"`, `version: 2`, and an empty `data` object (`{}`).

## Trigger

A client issues an HTTP request to `GET /api/where/report-problem-with-trip/{id}?key=<key>&...` or `GET /api/where/report-problem-with-trip.json?key=<key>&tripId=<id>&...`.

## Main Success Scenario

1. The client supplies the trip ID either via query parameter `tripId` or as path segment `{id}`, along with an API key and optional query parameters (`serviceDate`, `vehicleId`, `stopId`, `code`, `userComment`, `userOnVehicle`, `userVehicleNumber`, `userLat`, `userLon`, `userLocationAccuracy`). Note: `stopId` in this endpoint is an optional parameter indicating the transit stop where the problem occurred, whereas `tripId` is the trip identifier.
2. The server extracts the target trip ID using `extractAgencyCodeID` ([`report_problem_with_trip_handler.go#L19`](../internal/restapi/report_problem_with_trip_handler.go#L19), [`id_helpers.go#L35-L63`](../internal/restapi/id_helpers.go#L35-L63)). If `tripId` is present in the query string, it takes precedence over path `{id}` (matching legacy Java Struts, where `setTripId` calls `setId` and overwrites the path value). If `tripId` is absent from the query string, the server falls back to path segment `{id}` (with any `.json` extension stripped by [`utils.ExtractIDFromParams`](../internal/utils/http.go#L9-L12)). The server splits the combined ID on the first underscore character to obtain the agency ID and raw trip ID.
3. The server parses and validates floating-point parameters (`userLat`, `userLon`, `userLocationAccuracy`) and boolean parameter `userOnVehicle`.
4. If `userComment` is present, the server truncates the text to a maximum length of 500 characters.
5. The server records the report into the database with `trip_id`, `service_date`, `vehicle_id`, `stop_id`, `code`, `user_comment`, `user_on_vehicle`, `user_vehicle_number`, coordinates, accuracy, and server timestamps ([`report_problem_with_trip_handler.go#L65-L89`](../internal/restapi/report_problem_with_trip_handler.go#L65-L89)).
6. The server returns HTTP 200 with an empty OK response envelope (`data: {}`) ([`ReportProblemWithTripAction.java#L142`](https://github.com/OneBusAway/onebusaway-application-modules/blob/095bf1ac3aeb7009b9f78e7f1cb4c65bd38b988a/onebusaway-api-webapp/src/main/java/org/onebusaway/api/actions/api/where/ReportProblemWithTripAction.java#L142), [`report_problem_with_trip_handler.go#L91`](../internal/restapi/report_problem_with_trip_handler.go#L91)).

## Extensions

**1a. The trip ID is missing or empty:**
- When neither a query parameter `tripId` nor a path `{id}` is supplied (e.g. `GET /api/where/report-problem-with-trip.json?key=TEST`), or if the resolved ID is empty, the server returns HTTP 400 with `code: 400`, `text: "id cannot be empty"`, and `data.fieldErrors.tripId` (or `data.fieldErrors.id` when using the path route). An unrouted path request to `/api/where/report-problem-with-trip/` returns HTTP 404 before handler invocation.

**1b. Trip ID contains no underscore (malformed combined ID):**
- If the resolved trip ID contains no underscore delimiter (e.g. `report-problem-with-trip/nounderscore.json` or `report-problem-with-trip.json?tripId=not-combined`), the server returns HTTP 400 with `code: 400` and `text: "invalid format: <id>"`, with the error reported in `data.fieldErrors.tripId` (if from query) or `data.fieldErrors.id` (if from path). *(Note: Legacy Java threw an unhandled exception via `AgencyAndIdLibrary.convertFromString` resulting in an HTTP 500 error envelope; Maglev's HTTP 400 validation error is an intentional deviation.)*

**2a. Malformed floating-point query parameters (`userLat`, `userLon`, `userLocationAccuracy`):**
- The server rejects non-numeric strings, NaN, or infinite values with HTTP 400 and a JSON validation error response containing `data.fieldErrors`.

**2b. Malformed boolean query parameter (`userOnVehicle`):**
- Non-empty values other than case-insensitive `true` or `false` (e.g. `1`, `0`, `yes`, `bad`) are rejected with HTTP 400 and `fieldErrors["userOnVehicle"]`. When omitted or passed as an empty value (`?userOnVehicle=`), Maglev stores SQL `NULL` (`Valid: false`) rather than `false`.

**3a. Database failure or database uninitialized:**
- For non-context database errors, the server logs the error and returns HTTP 500 with a standard JSON error envelope (`"internal server error"`, `version: 2`). If a context timeout occurs (`context.DeadlineExceeded`), the server returns HTTP 504; client cancellations use `clientCanceledResponse`.

**4a. Missing or invalid API key:**
- The server returns HTTP 401 with `code: 401` and `text: "permission denied"`.

## Suspected Defects

### Defects that affect the use case

**1. Error response version hardcoded to 1 (defect DC-10).**

In legacy Java Struts, `ExceptionInterceptor.getExceptionAsResponseBean` ([line 72](https://github.com/OneBusAway/onebusaway-application-modules/blob/095bf1ac3aeb7009b9f78e7f1cb4c65bd38b988a/onebusaway-api-webapp/src/main/java/org/onebusaway/api/actions/api/ExceptionInterceptor.java#L72)) constructs error response envelopes with hardcoded `version: 1` regardless of the version requested by the client (version 2), and serializes the raw unhandled exception message in the `text` field. Successful responses use `version: 2`.

*Maglev intentionally corrects this — see [Implementation Decisions](#implementation-decisions).*

**2. Parameter casing mismatch between Java Struts and OpenAPI (#1715).**

The OpenAPI specification (`testdata/openapi.yml`) specifies `vehicleID` and `stopID` (with uppercase `ID`) as query parameters for `/api/where/report-problem-with-trip/{tripID}.json`. Official generated SDKs (such as the TypeScript / JavaScript SDK) send `vehicleID` and `stopID`. However, in Java OneBusAway (`ReportProblemWithTripAction.java#L64-L68`), Struts binds parameters to bean setters (`setVehicleId` and `setStopId`). Because Struts property binding is case-sensitive, query parameters sent with uppercase `ID` are silently ignored and stored as `null`.

## Implementation Decisions

**Standardized 500 error envelope with version 2 (PR #1641, defect DC-10).**

When a non-context database persistence error occurs or the database is uninitialized, Maglev returns a standard OneBusAway JSON error envelope with HTTP status 500, `Content-Type: application/json`, `"version": 2`, `"code": 500`, and `"text": "internal server error"`. (Context deadline expirations return HTTP 504, and canceled requests return client-canceled responses.) This addresses defect DC-10 and avoids leaking internal database exception strings or returning plain text errors.

**Query-string tripId precedence and mobile client routing (#1726, #1757).**

Maglev routes both `GET /api/where/report-problem-with-trip/{id}` and `GET /api/where/report-problem-with-trip.json`. A non-empty query parameter `tripId` wins over the path `{id}`: Java applied the path ID first and the query string after it, and `setTripId` called `setId`, so query parameter `tripId` overwrites the path ID (e.g., `/report-problem-with-trip/1_path.json?tripId=1_query` stores `query`). When `tripId` is absent from the query string, the path ID is used as the fallback.

This supports Android (which submits `report-problem-with-trip.json?tripId=...` without a path ID) and iOS (which also submits `tripId` in the query string). When a query ID is missing or malformed, the validation failure is reported under `data.fieldErrors.tripId`; when the fallback path ID fails validation, the error is reported under `data.fieldErrors.id`. Note that `stopId` in this endpoint is an optional parameter referencing the transit stop associated with the problem report (persisted to database column `stop_id`), not the trip identifier.

**Malformed ID handling (HTTP 400 vs. Java exception).**

In legacy Java, `AgencyAndIdLibrary.convertFromString` threw an unhandled runtime exception when a combined ID was missing an underscore delimiter, producing an HTTP 500 error envelope. Maglev intentionally validates the combined ID format and returns HTTP 400 with a structured `fieldErrors` response (`"invalid format: <id>"`).

**Parameter casing for vehicleId and stopId (#1715).**

Maglev currently reads `vehicleId` and `stopId` (with lowercase `d`) to maintain exact parity with Java Struts parameter binding. Requests sending uppercase `vehicleID` or `stopID` (such as calls from OpenAPI-generated SDKs) are currently ignored and stored as `NULL`. Supporting both parameter casings is tracked in [#1715](https://github.com/OneBusAway/maglev/issues/1715).

**Omitted optional parameters and deviations from legacy (PR #1641).**

When optional string query parameters (`vehicleId`, `stopId`, `code`, `userComment`, `userVehicleNumber`) are omitted or empty, Maglev persists them as SQL `NULL` values using `nulls.NonEmptyString`, matching legacy Java Struts behavior where unpopulated bean properties remain `null`. Omitted coordinate parameters (`userLat`, `userLon`, `userLocationAccuracy`) are likewise stored as SQL `NULL`, matching Java.

However, Maglev intentionally deviates from legacy Java in the following omitted field behaviors:
- **`serviceDate`**: Maglev stores SQL `NULL` when omitted or empty (using `nulls.NonEmptyString`). Legacy Java stored primitive `long` `0`.
- **`userOnVehicle`**: Maglev stores SQL `NULL` when omitted or empty (`?userOnVehicle=`), and `1` (true) or `0` (false) when provided (`sql.NullInt64{Int64: onVehicleValue, Valid: query.Get("userOnVehicle") != ""}`). Legacy Java stored primitive `boolean` `false`.

**Unknown trip IDs.**

In legacy Java (`UserReportingServiceImpl.reportProblemWithTrip`), if the trip cannot be resolved from the static GTFS schedule (`trip == null`), the method returns early and silently drops the problem report without saving it. Maglev persists problem reports for any validly-formatted trip ID regardless of whether the trip exists in the GTFS database.

**Ignored legacy parameters (data, time).**

Legacy Java Struts action `ReportProblemWithTripAction` included setters for `data` and `time` (via `ProblemReportBean`). Maglev does not persist or process these parameters and silently ignores them.

**Strict float and boolean parameter validation (PR #1490, [[Boolean-Query-Parameters]]).**

Maglev strictly validates `userLat`, `userLon`, and `userLocationAccuracy` using `utils.ParseFloatParam`. Malformed strings (including `garbage`, `NaN`, `Inf`, and `1e999`) are rejected with HTTP 400 and an explicit `fieldErrors` structure. Explicit `0` coordinate values are preserved. For `userOnVehicle`, malformed non-empty values (such as `1`, `0`, or `bad`) return HTTP 400, while omitted or empty values store SQL `NULL` without error.

**User comment length limit.**

User comments are truncated to 500 characters (`utils.MaxCommentLength`) before storage to guard against unbounded payloads while preserving rider feedback.

**Deprecated API status.**

Problem reporting endpoints are in scope for Maglev 1.0 to preserve backward compatibility with legacy mobile clients, but the problem-reporting feature is deprecated per [[Maglev-1.0-Endpoint-Scope]] and is a candidate for redesign in a future API version.

## Response Structure

### Envelope

```json
{
  "type": "object",
  "properties": {
    "version":     { "type": "integer" },
    "code":        { "type": "integer" },
    "text":        { "type": "string" },
    "currentTime": { "type": "integer", "description": "Unix milliseconds" },
    "data":        { "type": "object" }
  },
  "required": ["version", "code", "text", "currentTime"]
}
```

**`version`** — `2` for Maglev responses and legacy success/validation responses; legacy Java unhandled server error envelopes use `version: 1` (see Defect DC-10).

**`code`** — HTTP status code (`200` on success, `400` for validation error, `401` for unauthorized key, `500` for server error, `504` for deadline exceeded).

**`text`** — Human-readable status description (`"OK"` on success, `"internal server error"`, `"permission denied"`, etc.).

**`currentTime`** — Server wall-clock time in Unix milliseconds when the response was constructed.

**`data`** — On success, an empty JSON object (`{}`). On validation errors, an object containing `fieldErrors`. Omitted on Maglev HTTP 500 server error responses.
